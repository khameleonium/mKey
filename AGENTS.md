# AGENTS.md — правила для ИИ-агентов в проекте mKey

mKey — макросер ввода для Linux (аналог AutoHotKey) для X11 и Wayland. Backend на Go (один статический бинарник), GUI — веб (Svelte 5 + TS), встроенный в бинарник.

**Перед любой работой прочитай `SPEC.md`**: минимум §3 (ключевые решения), §4 (архитектура) и раздел, к которому относится твоя задача. Задачи и их статусы — в `SPEC.md` §13.

---

## 1. Как брать и закрывать задачи

1. Бери задачи **по порядку фаз** (§13). Внутри фазы — любую, у которой выполнены зависимости (`← T…`).
2. Взял задачу — отметь `[~]` в `SPEC.md`. Закончил — `[x]` и короткая заметка (что сделано, какие ограничения остались).
3. Задача готова (Definition of Done), когда:
   - код соответствует требованиям с указанными ID (`FR-…`, `NFR-…`, `SEC-…`);
   - есть тесты (unit обязательно; integration — если трогаешь evdev/uinput);
   - проходят `make lint` и `make test` (и `make test-integration`, если менялся ввод/вывод и есть `/dev/uinput`);
   - новые пользовательские строки есть в **ru и en**;
   - код прокомментирован по правилам §6.1 (doc-комментарии + комментарий к каждому логическому блоку);
   - модульные границы соблюдены (§4.1), `internal/archtest` зелёный;
   - обновлена документация (`docs/dsl.md`, `docs/lua-api.md`, `docs/openapi.yaml`, `docs/adapters.md` — что затронуто);
   - критерий приёмки фазы не сломан.
4. Не выполняй задачи из будущих фаз «заодно». Нашёл проблему вне задачи — запиши в «Открытые вопросы» (`SPEC.md` §14) или в заметку к задаче.

## 2. Когда нужен ADR (`docs/adr/NNNN-*.md`)

Обязательно, если ты:
- добавляешь **любую** внешнюю зависимость (Go или npm);
- вводишь cgo (разрешено только в опциональных модулях за build-тегом);
- меняешь грамматику DSL, формат YAML/`.mkrec`, API;
- отступаешь от решений D1–D15 из `SPEC.md` §3.

ADR и правка `SPEC.md` — в одном коммите/PR. Если решение неочевидно или затрагивает UX — **спроси владельца**, а не выбирай молча.

## 3. Команды

Go-модуль называется `mkey`. Репозиторий: https://github.com/khameleonium/mKey (публичный); пушить — только когда об этом просит владелец. Go 1.27 установлен в `/usr/local/go` (в `PATH` может не быть — тогда вызывай `/usr/local/go/bin/go` или добавь `export PATH=$PATH:/usr/local/go/bin:$HOME/go/bin`). `staticcheck` лежит в `~/go/bin`. В `go.mod` — `go 1.27`.

```bash
make build              # web + go build (CGO_ENABLED=0) → ./mkey и консольная ./mkey-cli
make build-cli          # только консольная версия ./mkey-cli (-tags nogui: без окна и трея, Node не нужен)
make web                # только фронтенд → web/dist
make test               # go test ./... + фронтенд-тесты (без прав и устройств)
make test-integration   # go test -tags integration ./test/integration/... (нужен /dev/uinput)
make lint               # golangci-lint, go vet, eslint, svelte-check, prettier --check
make fmt                # gofmt/goimports + prettier
make run                # собрать и показать справку; демон — ./mkey daemon
make gencodes           # перегенерировать коды клавиш из linux/input-event-codes.h
./mkey doctor           # диагностика окружения (только чтение)
./mkey send --dry-run '{A}'  # проверить запись макроса без нажатий (сам запустит демон)
./mkey daemon stop      # остановить фоновую часть
./mkey project list     # проекты; включение проекта с consume-хоткеями ЗАХВАТЫВАЕТ клавиатуру — не делай этого на машине разработчика без разрешения
./mkey debug devices    # список устройств ввода (временная команда фазы 1)
./mkey daemon --fake-backends   # демон без реальных устройств (для GUI и e2e)
```

`go build ./...` должен работать **без Node**: если `web/dist` не собран, пакет `web` встраивает заглушку `web/stub/index.html`. Не коммить собранный `web/dist` (в git только `web/dist/.gitkeep`).

## 4. Архитектурные правила

### 4.1 Модульность (SPEC §4.3) — главное правило

- **Каждая функция — модуль** с интерфейсом `Module` (`ID/Init/Start/Stop`), своими тестами, `doc.go`, секцией конфига, i18n-ключами `<module>.*` и папкой `web/src/features/<module>/`. Новый модуль создавай через `make new-module NAME=<id>`.
- **Модули не импортируют друг друга.** Нужна чужая функциональность → используй контракт из `internal/contracts` (получай его из реестра сервисов в `Init`) или события шины `internal/bus`. Нет подходящего контракта → добавь его в `internal/contracts` отдельным коммитом с обоснованием. Это проверяет архитектурный тест `internal/archtest` (ADR-0016, `docs/modules.md`); не ослабляй его правила без ADR.
- **Чистые библиотеки** без жизненного цикла (таблица клавиш, парсер DSL, часы) — в `internal/lib/<name>`: их может импортировать кто угодно, сами они импортируют только другие `internal/lib/*`.
- **Новые типы действий, триггеров, условий, команд DSL, адаптеров, шаблонов устройств, init-систем** и т.п. добавляются **регистрацией в точке расширения**, а не правкой `engine`/`dsl`/GUI. У каждого типа — метаданные и JSON Schema параметров: по ним GUI сам строит блок конструктора.
- Встроенные модули подключаются **явно** одной строкой в `internal/app/modules.go`. Никаких `init()` с побочными эффектами регистрации.
- Необязательный модуль должен отключаться без поломки остальных. Если твой код падает при отключённом соседнем модуле — это баг.
- Контракты и `pkg/pluginsdk` — публичные обещания плагинам: ломающее изменение только через ADR и новую мажорную версию `plugin_api`.

### 4.2 Платформы и окружения

- **Всё системно-зависимое** (init-система, повышение прав, доступ к устройствам, пакетный менеджер, пути автозагрузки модулей) — только в бэкендах `internal/platform/*`. **Не считай, что systemd есть**: никаких прямых вызовов `systemctl`, `pkexec`, `udevadm` вне соответствующего бэкенда.
- Системы без systemd (Void, Artix, Alpine, Devuan…) поддерживаются полностью (SPEC FR-INST-7) — проверяй, что изменение не ломает их бэкенды.

### 4.3 Прочие правила

- **Ввод/вывод — только evdev/uinput** (`internal/input`, `internal/output`). Никакого XTest, ydotool, keyd, xdotool.
- **`internal/engine` зависит только от контрактов** (`contracts.InputSource`, `contracts.VirtualDevices`, `contracts.WindowTracker`, `contracts.PixelReader`, `contracts.PointerLocator`, `contracts.LayoutProvider`, часы `clock.Clock`). Импорт конкретных адаптеров или бэкендов из `engine` запрещён.
- **Зависящее от окружения рабочего стола** (окна, пиксели, курсор, раскладка) — только в `internal/desktop/<adapter>`, каждый адаптер сообщает `Capabilities()`. Нет возможности — возвращай типизированную ошибку `contracts.ErrUnsupported` с понятным объяснением, не паникуй и не молчи.
- **Единый источник истины — YAML-модель** (`internal/store`). GUI и CLI меняют её только через API.
- **CLI — клиент того же HTTP API** через Unix-сокет. Не дублируй бизнес-логику в CLI.
- **Любая запись файла в систему** при установке — только через API манифеста (`internal/setup/manifest`), иначе удаление «без следов» сломается.
- **`mkey privileged`** — только белый список подкоманд, без аргументов-путей от пользователя; содержимое системных файлов зашито в бинарник.
- Время — через `clock.Clock` (в тестах — фейковые часы). Никаких `time.Sleep` в логике движка без контекста отмены.
- Все долгие операции принимают `context.Context` и корректно прерываются.

## 4a. Язык макросов (DSL) — решения владельца, не менять без согласования

- Клавиши — **только явные имена**, регистронезависимо: `{Ctrl}`, `{Shift}`, `{Enter}`, `{Mouse0}`. Никаких AHK-сокращений (`^` = Ctrl, `+` = Shift, `!` = Alt).
- В фигурных скобках — **всегда одна клавиша**, везде (макросы, горячие клавиши, системные сочетания): `{Ctrl+C}` — ошибка; сочетание пишется зажатием `^{Ctrl}{C}~{Ctrl}`, горячая клавиша — `^{Ctrl}^{Alt}{H}`. `^` дважды без `~` и `~` без `^` — ошибки (ADR-0025).
- Символы обозначают действия: `{Key}` — нажать, `^{Key}` — зажать, `~{Key}` — отпустить, `{Key 500}` — удерживать 500 мс, `[250]` — пауза, `{"текст"}` — набор текста с JSON-экранированиями (`\n` → Enter).
- Зажатые через `^{...}` модификаторы **действуют на набираемый текст**, как при ручном наборе: `^{Shift}{"Привет, Вера!"}~{Shift}` → `ПРИВЕТ, ВЕРА!`.
- Кнопки неизвестных устройств — авто-ID `{UnKey001}` (устройство `UnKey`, кнопка `001`), переименовываются в `{Sega.Start}`; авто-ID навсегда остаются рабочими алиасами (SPEC §5.6).
- Подробности — `SPEC.md` §5.1; грамматика — `docs/dsl.md`.

## 5. Безопасность ввода — критично

Ошибка в grab'е может оставить пользователя без клавиатуры. Поэтому:

- Любой код с `EVIOCGRAB` обязан поддерживать экстренную остановку (`Esc+Backspace+Enter`, SEC-1) и watchdog (SEC-3). Не выключай их даже в отладке.
- Любой путь остановки (отмена раннера, выход демона, паника в раннере) вызывает `ReleaseAll()` на виртуальных устройствах.
- Собственные виртуальные устройства (имя начинается с `mKey `) **всегда** исключаются из чтения — иначе будет петля обратной связи.
- **Не запускай на машине разработчика** тесты/команды, которые грабят реальные устройства, отправляют ввод в живую сессию, требуют `sudo`/`pkexec` или меняют `/etc`, без явного разрешения человека. Для таких проверок — CI, VM, headless sway, Xvfb или `--fake-backends`.
- Не логируй нажатия клавиш (NFR-8) и не добавляй телеметрию.
- Веб-API: только `127.0.0.1`, проверка токена/cookie, `Host` и `Origin` (SEC-5). Не ослабляй ради удобства разработки — для dev есть `--dev`, который сохраняет проверки.

## 6. Стиль кода

### 6.1 Комментарии — обязательное требование владельца

Код должен читаться человеком, который видит его впервые. Правила:

1. **Каждый пакет** — файл `doc.go`: назначение пакета, основные типы, как он связан с другими модулями, как его расширять.
2. **Каждый тип, функция, метод, константа/группа констант** (экспортируемые и нет) — doc-комментарий: *что делает*, что означают неочевидные параметры и результат, какие ошибки возвращает.
3. **Каждый логический блок внутри функции** (несколько строк, выполняющих один шаг: проверка входных данных, открытие устройства, цикл чтения событий, отправка, очистка) начинается с комментария, отвечающего на вопрос **«что делает этот блок»**. Тривиальные строки внутри блока отдельно не комментируются — их покрывает комментарий блока.
4. **Неочевидные решения** дополнительно объясняют **«почему»**: магические числа, тайминги, ioctl, обходы багов композиторов — со ссылкой на документацию ядра/протокола/issue.
5. Комментарии обновляются вместе с кодом. Устаревший комментарий — это баг.
6. То же во фронтенде: комментарий-шапка у каждого Svelte-компонента (что показывает, какие props), doc-комментарии у функций, комментарии к логическим блокам.

Пример ожидаемой плотности:

```go
// Tap нажимает и отпускает одну клавишу на виртуальной клавиатуре.
// Возвращает ошибку, если клавиша не поддерживается устройством или запись в устройство не удалась.
func (k *Keyboard) Tap(ctx context.Context, code keys.Code) error {
	// Проверяем, что клавиша входит в возможности (capabilities) этого устройства.
	if !k.caps.Has(code) {
		return fmt.Errorf("tap %s: %w", code, ErrUnsupportedKey)
	}

	// Отправляем нажатие и SYN_REPORT, чтобы композитор увидел событие.
	if err := k.emit(code, keyDown); err != nil {
		return fmt.Errorf("tap %s: press: %w", code, err)
	}

	// Ждём минимальное время удержания: некоторые игры игнорируют нажатия короче одного кадра.
	if err := k.clock.Sleep(ctx, k.minHold); err != nil {
		// Контекст отменён: всё равно отпускаем клавишу, чтобы она не «залипла».
		_ = k.emit(code, keyUp)
		return err
	}

	// Отправляем отпускание, завершая нажатие.
	return k.emit(code, keyUp)
}
```

### 6.2 Go
- Актуальная стабильная версия Go; `gofmt`/`goimports`, `golangci-lint` без предупреждений.
- Пакеты — в `internal/`; публичный пакет только один — `pkg/pluginsdk`. Интерфейсы **между модулями** — в `internal/contracts`; маленькие интерфейсы **внутри модуля** объявляются на стороне потребителя.
- Ошибки: `fmt.Errorf("...: %w", err)`; ошибки, видимые пользователю, — с кодом (`dsl.unknown_key`) и i18n-ключом.
- Логи: `log/slog`, структурированные поля.
- Тесты: табличные, `t.Parallel()` где безопасно; golden-файлы в `testdata/`; интеграционные — с `//go:build integration`.
- Без глобального изменяемого состояния; зависимости передаются явно (конструкторы).

### 6.3 Фронтенд
- Svelte 5 (runes), TypeScript strict, без `any` без комментария-обоснования.
- Строки UI — только через i18n-ключи (ru, en).
- Типы API генерируются из `docs/openapi.yaml`, не пиши их вручную.
- Код фичи — в `web/src/features/<module>/`; общий код — в `web/src/lib/`. Блоки конструктора строятся по метаданным `GET /api/v1/registry`, не хардкодь типы действий.
- Тексты для пользователя — простым языком, без жаргона; технические детали — под «Подробнее» (см. `SPEC.md` FR-UI-8).

### 6.4 Язык
- **Комментарии в коде — на русском** (решение владельца), включая doc-комментарии: `// Tap нажимает и отпускает…` (имя идентификатора в начале — по конвенции Go).
- Идентификаторы, строки логов, коды ошибок и сообщения коммитов — на английском.
- Документация в `SPEC.md`, `AGENTS.md`, `docs/` — на русском (допускается английский дубль).
- Пользовательский интерфейс и сообщения CLI — ru + en через i18n.

## 7. Коммиты

- Conventional Commits: `feat(dsl): parse hold duration`, `fix(input): retry open on EACCES`, `docs(adr): 0007 wayland client`.
- В теле — ссылки на ID требований и задач: `Refs: T2.2, FR-DSL-1, FR-DSL-3`.
- Один логический шаг — один коммит. Не смешивай рефакторинг и фичу.
- Не коммить и не пушь, если человек об этом не просил.

## 9. Если не уверен

- Требование противоречиво или неполно → предложи вариант, запиши вопрос в `SPEC.md` §14 и спроси человека; не изобретай поведение, видимое пользователю, молча.
- Поведение зависит от композитора → проверь по документации композитора/протокола, зафиксируй в `docs/adapters.md`, а не полагайся на память.
- Не можешь проверить что-то локально (нет Wayland/GNOME/KDE, нет `/dev/uinput`) → прямо напиши об этом в заметке к задаче и укажи, что нужно проверить вручную.
