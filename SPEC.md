## 1. Цель и позиционирование

**mKey** — макросер ввода для Linux, аналог AutoHotKey, рассчитанный на обычного пользователя:

- работает одинаково в **X11 и Wayland** (GNOME, KDE Plasma, Sway, Hyprland и другие wlroots-композиторы);
- настраивается через **веб-интерфейс** с визуальным конструктором (блоки + система событий в духе Construct 3 / GameMaker, но проще) **и** полностью через терминал (CLI + читаемые YAML-файлы);
- умеет: отправлять нажатия, записывать и повторять действия пользователя (клавиатура, мышь, тач), реагировать на комбинации клавиш, заголовки окон, цвет пикселя; распознавать неизвестные устройства и подписывать их кнопки; создавать виртуальные устройства (клавиатуры, мыши, геймпады, тач-экраны);
- **модульный и расширяемый**: каждая функция — отдельный модуль, который можно дорабатывать и отключать независимо; сторонние разработчики пишут плагины (новые действия, триггеры, поддержку других систем и окружений);
- **прозрачен**: сам диагностирует систему, сам объясняет простым языком, что ему нужно, и просит согласия; устанавливается и удаляется без следов (или с сохранением настроек).

**Не цель v1:** поиск изображений на экране, OCR, сетевые триггеры (доступны через плагины), macOS/Windows.

## 2. Глоссарий

| Термин | Значение |
|---|---|
| **Демон (`mkeyd`)** | Фоновый процесс mKey от имени пользователя (не root). Тот же бинарник `mkey`, режим `mkey daemon`. |
| **evdev** | Интерфейс ядра `/dev/input/event*` — чтение событий физических устройств. Работает одинаково в X11 и Wayland. |
| **uinput** | Интерфейс ядра `/dev/uinput` — создание виртуальных устройств ввода. Композитор/X-сервер видит их как настоящие. |
| **Grab** | `EVIOCGRAB` — эксклюзивный захват физического устройства: события получает только mKey, а в систему они уходят через виртуальный «проходной» (passthrough) клон. Нужен для блокировки/переназначения клавиш. |
| **Проект (Project)** | Набор событий и настроек, файл `*.mkey.yaml`. Можно включать/выключать проекты целиком. |
| **Событие (Event)** | Строка «листа событий»: триггер(ы) + условия + список действий. |
| **Триггер** | Что запускает событие: горячая клавиша, окно, пиксель, таймер, подключение устройства и т.д. |
| **Условие** | Дополнительная проверка в момент срабатывания (активное окно, состояние клавиши, переменная, пиксель). |
| **Действие** | Шаг сценария: нажать, отпустить, пауза, мышь, цикл, Lua, bash… |
| **DSL** | Текстовый язык последовательностей mKey (`^{Mouse0}[500]~{Mouse0}`), см. §5.1. |
| **Адаптер** | Модуль, реализующий зависящую от окружения возможность (активное окно, пиксель, позиция курсора, раскладка) для конкретного композитора. |
| **Capability** | Флаг «эта возможность доступна в текущей сессии». GUI обязан честно показывать недоступные возможности. |
| **Метка устройства** | Пользовательское имя устройства и его кнопок («Левая педаль», «Кнопка G1»). |
| **Авто-ID (UnKey)** | Автоматическое имя неизвестного устройства и его кнопок: `{UnKey001}` — кнопка 001 устройства UnKey. Переименовывается пользователем (§5.6). |
| **Модуль** | Самостоятельная часть программы с собственным жизненным циклом, конфигом и тестами (запись, инспектор, адаптер GNOME…). Модули не импортируют друг друга (§4.3). |
| **Контракт** | Go-интерфейс в `internal/contracts`, через который модули пользуются друг другом. |
| **Точка расширения** | Реестр, в который модуль или плагин добавляет новый тип: действие, триггер, условие, адаптер, шаблон устройства, init-систему… |
| **Плагин** | Внешнее расширение: Lua-плагин или отдельный процесс на любом языке (JSON-RPC через stdio), §5.12. |
| **Платформенный бэкенд** | Реализация системно-зависимой операции: init-система (systemd, OpenRC, runit…), повышение прав (pkexec, sudo, doas), доступ к устройствам (uaccess, группа, mdev). |

## 3. Ключевые технические решения

| # | Решение | Обоснование |
|---|---|---|
| D1 | **Ввод и вывод — только через evdev/uinput**, а не через X11 XTest / Wayland-протоколы | Единственный путь, одинаково работающий в X11 и во всех Wayland-композиторах. Wayland не даёт клиентам глобально читать/эмулировать ввод. |
| D2 | **Backend — Go, один статический бинарник, `CGO_ENABLED=0`** для ядра | Простая установка «скачал и запустил», без зависимостей от версий системных библиотек. cgo допускается только в опциональных модулях за build-тегом (ADR обязателен). |
| D3 | **Демон работает от пользователя**, привилегированные операции — только разовые, через `pkexec mkey privileged <фиксированная-команда>` | Минимум прав. Root нужен лишь для установки udev-правил и загрузки модуля `uinput`. |
| D4 | **Доступ к устройствам — через udev-тег `uaccess`** (ACL для пользователя активной сессии), запасной путь — группа `input` | `uaccess` не требует перелогина и не выдаёт доступ удалённым/неактивным сессиям. Так делает, например, Steam для `/dev/uinput`. |
| D5 | **Не используем ydotool и keyd как зависимости** | Оба — тонкие обёртки над тем же uinput/evdev, которые мы и так используем напрямую. Их демоны конфликтовали бы с нашим grab'ом, а зависимость усложнила бы установку. Их код — хороший референс (см. §11). |
| D6 | **Окружение-зависимые функции — через адаптеры с capability-флагами** | На Wayland нет универсального API для заголовка окна и пикселей; каждый композитор делает это по-своему. |
| D7 | **Единая модель проекта (YAML) — единственный источник истины**. GUI, CLI и ручное редактирование работают с одной моделью | Нет рассинхронизации «GUI-формат vs текст». |
| D8 | **GUI — веб (Svelte 5 + TypeScript + Vite)**, собранный фронтенд встраивается в бинарник через `go:embed` | Не нужен отдельный GUI-тулкит; открывается в любом браузере. |
| D9 | **Один API — два транспорта**: HTTP+WebSocket на `127.0.0.1` для браузера и тот же HTTP поверх Unix-сокета для CLI | CLI и GUI используют одинаковые эндпоинты — меньше кода и тестов. |
| D10 | **Lua — gopher-lua (Lua 5.1, pure Go)** | Без cgo, легко встраивается, простые биндинги. |
| D11 | **Все установленные файлы фиксируются в манифесте** | Гарантирует удаление «без следов». |
| D12 | **Модульная архитектура**: модули + контракты + реестр точек расширения; модули не импортируют друг друга (проверяется архитектурным тестом `internal/archtest`, ADR-0016) | Каждую функцию можно дорабатывать, тестировать и отключать отдельно; новые возможности добавляются без правки ядра. |
| D13 | **Плагины — Lua-плагины и плагины-процессы (JSON-RPC 2.0 через stdio)**; Go `plugin` (.so) не используем | Процесс-плагин можно написать на любом языке, его падение не роняет демон; `.so`-плагины Go требуют точного совпадения тулчейна и cgo. |
| D14 | **Системные различия — через платформенные бэкенды** (`internal/platform`): systemd — один из бэкендов, а не допущение | Полная поддержка дистрибутивов без systemd (OpenRC, runit, dinit, s6, sysvinit) и простое добавление новых. |
| D15 | **Код подробно комментируется**: у каждого пакета, типа и функции — doc-комментарий, у каждого логического блока внутри функции — комментарий «что делает этот блок» | Читаемость для людей и ИИ-агентов, независимая доработка модулей. Правила — `AGENTS.md` §6. |

## 4. Архитектура

```
                ┌───────────────────────── mkey (один бинарник) ─────────────────────────┐
 Браузер ──HTTP/WS──►│ api ◄──────────┐                                                   │
 (127.0.0.1)         │                │                                                   │
 CLI `mkey ...` ─unix sock─► api      │                                                   │
                     │                ▼                                                   │
                     │   store (YAML, hot-reload) ──► engine (события, планировщик)       │
                     │                                  │   ▲          │                   │
                     │                    ┌─────────────┘   │          ▼                   │
                     │                    ▼                 │     script (lua, shell)      │
                     │     dsl (parser → AST → actions)     │                              │
                     │                    │                 │                              │
                     │                    ▼                 │                              │
                     │          output (vdev manager) ──────┼──► uinput ──► ядро ──► X11/Wayland
                     │                                      │                              │
                     │   input (evdev reader, grab, hotplug) ──► hotkeys / recorder / inspector
                     │                                      │                              │
                     │   desktop adapters: x11 | gnome | kde | sway | hyprland | wlroots | portal
                     │   setup (doctor, permissions, install/uninstall)                   │
                     └────────────────────────────────────────────────────────────────────┘
       Внешние компоненты (ставятся по согласию): udev-правило, systemd --user unit,
       .desktop/автозапуск, GNOME Shell extension (mkey@mkey), KWin-скрипт.
```

### 4.1 Модули и границы

- `input` — перечисление устройств, hotplug (fsnotify на `/dev/input` + повтор при `EACCES`, т.к. ACL применяется с задержкой), чтение событий, grab, passthrough. Публикует события в шину (`bus`). Игнорирует **собственные** виртуальные устройства mKey (по имени-префиксу `mKey ` и `phys` = `mkey/...`), чтобы не было петель обратной связи.
- `output` — менеджер виртуальных устройств (vdev): создание по шаблону, учёт «зажатых» клавиш, безопасное отпускание всего при остановке.
- `lib/keys` — библиотека: таблица имён клавиш ↔ кодов evdev, алиасы, локализованные подписи.
- `lib/dsl` — библиотека: лексер, парсер, AST, валидация, форматирование (AST → текст) и компиляция в список действий.
- `engine` — загрузка проектов, регистрация триггеров, проверка условий, выполнение действий (каждый запуск события — отдельная горутина-«раннер» с контекстом отмены), переменные, политики повторного запуска.
- `script/lua`, `script/shell` — исполнители скриптов.
- `recorder` — запись и воспроизведение.
- `desktop` — интерфейсы `WindowTracker`, `PixelReader`, `PointerLocator`, `LayoutProvider` и их реализации по адаптерам.
- `session` — определение окружения: `XDG_SESSION_TYPE`, `WAYLAND_DISPLAY`, `DISPLAY`, `XDG_CURRENT_DESKTOP`, сокеты `SWAYSOCK`, `HYPRLAND_INSTANCE_SIGNATURE` и т.п.
- `setup` — диагностика (`doctor`), выдача прав, установка/удаление, манифест.
- `store` — конфиг, проекты, метки устройств, миграции версий схемы.
- `api` — HTTP-роутер, WebSocket-стримы, аутентификация.

**Правило зависимостей:** `engine` зависит только от интерфейсов (`output.Sink`, `input.Source`, `desktop.*`), а не от конкретных бэкендов. Это позволяет тестировать движок на фейках без `/dev/uinput`.

### 4.2 Потоки данных (ключевые сценарии)

1. **Горячая клавиша:** evdev → `input` → `hotkeys.Matcher` → (если `consume` — событие не пробрасывается в passthrough) → `engine` запускает раннер → действия → `output` → uinput.
2. **Запись:** evdev (выбранные устройства) → `recorder` с временными метками ядра → файл записи → конвертация в действия/DSL.
3. **Триггер окна:** адаптер эмитит `WindowChanged{title, app_id, pid}` (по сигналу или опросу) → `engine`.
4. **Триггер пикселя:** `engine` раз в тик собирает все точки активных пиксельных триггеров → один батч-запрос к `PixelReader` → сравнение с допуском → срабатывание по фронту.

### 4.3 Модульность и расширяемость

**Принципы:**
1. **Каждая функция — модуль.** Пакеты из §4.1 (кроме ядра) оформлены как модули с единым интерфейсом:
   ```go
   // Module — самостоятельная часть функциональности mKey со своим жизненным циклом.
   type Module interface {
       // ID возвращает уникальный идентификатор модуля, например "recorder".
       ID() string
       // Init получает зависимости от хоста и регистрирует точки расширения.
       Init(ctx context.Context, host Host) error
       // Start запускает фоновую работу модуля.
       Start(ctx context.Context) error
       // Stop останавливает модуль и освобождает все его ресурсы (включая зажатые клавиши).
       Stop(ctx context.Context) error
   }
   ```
   `Host` даёт модулю: реестр сервисов (контракты), шину событий, свою секцию конфига, логгер, i18n и реестры точек расширения.
2. **Модули не импортируют друг друга.** Общение — только через контракты из `internal/contracts` (получаются из реестра сервисов) и через шину `bus`. Чистые библиотеки без жизненного цикла (`keys`, `dsl`, `clock`, `buildinfo`) живут в `internal/lib/*` и доступны всем. Правила проверяет архитектурный тест `internal/archtest` (ADR-0016, `docs/modules.md`): модуль `internal/<X>` может импортировать только `internal/contracts`, `internal/registry`, `internal/bus`, `internal/i18n`, `internal/lib/*`, свои подпакеты и сторонние библиотеки.
3. **Ядро минимально:** `daemon`, `registry`, `bus`, `contracts`, `store`, `api`, `input`, `output`, `engine`, `platform` (плюс библиотеки `internal/lib/*`). Всё остальное (`hotkeys`, `recorder`, `inspector`, `vdev`-привязки, `script/lua`, `script/shell`, каждый десктоп-адаптер, трей, обновления, хост плагинов) — **необязательные модули**, отключаемые в `config.yaml`:
   ```yaml
   modules:
     recorder: { enabled: true }
     desktop.gnome: { enabled: false }
   ```
   Демон обязан стартовать и работать при отключении любого необязательного модуля (проверяется тестом, §12).
4. **Явная сборка:** встроенные модули перечислены в одном файле `internal/app/modules.go` (без магии `init()`), чтобы полный состав программы был виден в одном месте. Необязательные модули можно исключить build-тегами.
5. **Каждый модуль** имеет: `doc.go` (назначение, как устроен, как расширять), собственные тесты, собственную секцию конфига с JSON Schema, собственные i18n-ключи (`<module>.*`), страницу/компоненты во фронтенде в `web/src/features/<module>/`.

**Точки расширения** (реестры в `internal/registry`; одинаково доступны встроенным модулям и плагинам):

| Точка | Контракт | Примеры реализаций |
|---|---|---|
| Тип триггера | `contracts.TriggerType` | hotkey, window, pixel; плагин «MIDI», «HTTP-вебхук» |
| Тип условия | `contracts.ConditionType` | window, key_state, variable |
| Тип действия | `contracts.ActionType` | send, repeat, lua; плагин «HTTP-запрос» |
| Команда DSL | `contracts.DSLCommand` | `{Move ...}`, `{Wheel ...}`; плагин `{Midi ...}` |
| Десктоп-адаптер | `contracts.DesktopAdapter` | x11, gnome, kde, sway, hyprland, wlroots, portal |
| Шаблон виртуального устройства | `contracts.DeviceTemplate` | xbox360, ds4, touchscreen |
| Профиль устройства | `contracts.DeviceProfile` (данные) | «Sega USB Joystick»: имена кнопок (§5.6) |
| Init-система / автозапуск | `contracts.InitSystem` | systemd, openrc, runit, dinit, s6, sysvinit, xdg-autostart, compositor-config |
| Повышение прав | `contracts.Elevator` | pkexec, sudo/doas в окне терминала, «команда для копирования» |
| Доступ к устройствам | `contracts.DeviceAccess` | uaccess, group-input, mdev |
| Пакетный менеджер | `contracts.PackageManager` | apt, dnf, pacman, zypper, xbps, apk, emerge |
| Расширение Lua API | `contracts.LuaExtension` | добавляет `mkey.<ns>.*` |
| Маршруты API | `contracts.RouteProvider` | `/api/v1/<module>/...` |

У каждого зарегистрированного типа есть **метаданные**: ID, локализованное имя и описание, категория, иконка, **JSON Schema параметров**, требуемые capabilities. GUI получает их из `GET /api/v1/registry` и **строит блоки конструктора и формы автоматически** — новое действие из модуля или плагина появляется в конструкторе без правки фронтенда. Для сложных блоков модуль может поставлять собственный компонент редактора.

**Версионирование:** контракты и `pkg/pluginsdk` версионируются по semver (`plugin_api: 1.x`). Ломающее изменение — только через ADR и повышение мажорной версии API плагинов.

## 5. Функциональные требования

Каждое требование имеет ID (`FR-...`) — ссылайтесь на него в коммитах и тестах.

### 5.1 Язык последовательностей (mKey DSL)

Цель: максимально понятная запись «нажать / зажать / отпустить / подождать». DSL используется в действии `send`, в CLI `mkey send`, в Lua `mkey.send()`, в bash `mkey send`, а блоки конструктора отображают свой DSL-эквивалент.

**Принцип (решение владельца):** все клавиши называются **явно и полным именем** — `{Ctrl}`, `{Shift}`, `{Alt}`, `{Enter}`. Никаких символьных сокращений клавиш в стиле AHK (`^` = Ctrl, `+` = Shift, `!` = Alt) нет. Служебные символы обозначают только **действия**:

| Символ | Действие |
|---|---|
| `{Key}` | нажать и отпустить (однократное нажатие) |
| `^{Key}` | зажать (и держать, пока не отпустят) |
| `~{Key}` | отпустить (отжать) |
| `{Key 500}` | удерживать 500 мс, затем отпустить |
| `[250]` | пауза 250 мс между действиями |
| `{"текст"}` | набрать текст |

**FR-DSL-1. Конструкции (окончательная грамматика в EBNF — `docs/dsl.md`, фаза 2):**

| Запись | Значение |
|---|---|
| `{A}` | нажать и отпустить клавишу A (физическую клавишу, **без** Shift — см. ниже про регистр) |
| `^{Mouse0}` | зажать левую кнопку мыши |
| `~{Mouse0}` | отпустить левую кнопку мыши |
| `~{*}` | отпустить всё, что зажато этой последовательностью/раннером |
| `{Space 500}` | удерживать `Space` 500 мс, затем отпустить |
| `{A*3}` | нажать `A` 3 раза (интервал по умолчанию из настроек, 30 мс) |
| `{Ctrl+Shift+T}` | аккорд (сокращение): то же, что `^{Ctrl}^{Shift}{T}~{Shift}~{Ctrl}` |
| `[250]` / `[1.5s]` | пауза 250 мс / 1,5 с |
| `[100..300]` | случайная пауза от 100 до 300 мс |
| `{"ABCabc\nAAA"}` | набрать текст `ABCabc`, Enter, `AAA` (§ «Набор текста» ниже) |
| `( {A}[50]{B} )*10` | группа с повтором |
| `{Move 100 200}` | переместить курсор в абсолютную точку экрана (px) |
| `{Move +10 -5}` | относительное перемещение |
| `{Click 100 200}` | переместить и нажать `Mouse0` (сахар) |
| `{Wheel Up 3}` / `{Wheel Left}` | прокрутка |
| `{Touch 500 800}` / `{Swipe 100 800 100 200 300}` | тап / свайп (x1 y1 x2 y2 мс) на виртуальном тач-экране |
| `{pad2.South}` / `^{pad2.LT}` | кнопка виртуального устройства `pad2` |
| `{pad2.LX=0.5}` | установить ось (нормализованное значение −1..1, для триггеров 0..1) |
| `{UnKey001}` / `{UnKey.001}` | кнопка 001 неизвестного устройства UnKey (авто-ID, §5.6) |
| `{Sega.Start}` | та же кнопка после переименования (устройство → `Sega`, кнопка 001 → `Start`) |
| `{UnKey.Axis01=0.5}` | ось неизвестного устройства |
| `{#30}` / `{#0x110}` | сырой код evdev |
| `// комментарий` | до конца строки |
| `\{`, `\[`, `\\` | экранирование служебных символов вне текста |

Пробелы и переводы строк между элементами игнорируются (можно форматировать макрос по строкам). Текст вне `{"..."}` — ошибка с подсказкой «чтобы набрать текст, заключите его в `{"..."}`».

**Имена клавиш (`internal/lib/keys`)** — **регистронезависимы** (`{ctrl}`, `{Ctrl}`, `{CTRL}` — одно и то же); форматтер приводит их к каноническому виду из таблицы. Основные: буквы/цифры (`A`, `1`), `F1..F24`, `Enter`, `Esc`, `Tab`, `Space`, `Backspace`, `Up/Down/Left/Right`, `Home/End/PgUp/PgDn`, `Insert/Delete`, `Ctrl/LCtrl/RCtrl`, `Shift/LShift/RShift`, `Alt/LAlt/RAlt` (`AltGr`), `Super/LSuper/RSuper` (алиасы `Win`, `Meta`), `CapsLock`, `PrintScreen`, `Pause`, медиа-клавиши (`VolumeUp`, `PlayPause`…), `Num0..Num9`, `NumEnter`…
Без префикса `L/R`: при **отправке** используется левая клавиша, при **распознавании** хоткея подходит любая.
Мышь: `Mouse0` = левая, `Mouse1` = правая, `Mouse2` = средняя, `Mouse3` = «назад», `Mouse4` = «вперёд», далее `Mouse5+`. Геймпад (стандарт Linux): `South/East/North/West` (алиасы `A/B/Y/X` в стиле Xbox — только с префиксом устройства), `LB/RB/LT/RT`, `LS/RS`, `Start/Select/Mode`, `DPadUp...`, оси `LX/LY/RX/RY`.
Имена клавиш — **физические позиции (US-раскладка)**, как в evdev: `{Q}` на русской раскладке даст «й», а `{A}` — строчную «a» (регистр в имени клавиши ничего не значит). Для заглавной буквы — `{"A"}` или `^{Shift}{A}~{Shift}`.

**Набор текста `{"..."}` (FR-DSL-1a):**
- Строка — как строковый литерал **JSON**: экранирования `\"`, `\\`, `\/`, `\n` (→ `Enter`), `\t` (→ `Tab`), `\b` (→ `Backspace`), `\r` (→ `Enter`; пара `\r\n` — один `Enter`), `\uXXXX` (включая суррогатные пары). Неизвестное экранирование — ошибка парсера. `\f` — ошибка («не поддерживается»).
- Каждый символ набирается **так, как при обычном наборе человеком** в текущей раскладке: mKey находит физическую клавишу и нужные модификаторы (Shift/AltGr) для символа (§5.8, FR-AD-4).
- **Взаимодействие с зажатыми модификаторами** (ключевое поведение): модификаторы, зажатые через `^{...}`, **остаются зажатыми и действуют на набор**, как если бы человек держал их пальцем:
  - если символу и так нужен Shift — он нажимается как обычно (символ не меняется);
  - если символу Shift не нужен — зажатый Shift действует на его клавишу (строчная → заглавная, цифра → символ над ней и т.д.).
  - Пример: `^{Shift}{"Привет, Вера!"}~{Shift}{Enter}` в русской раскладке → `ПРИВЕТ, ВЕРА!` и перевод строки (запятая и `!` в русской раскладке и так набираются с Shift, поэтому не меняются; пробел Shift не меняет). В раскладке US та же последовательность с `{"a,b"}` даст `A<B` — ровно как на реальной клавиатуре.
  - То же для других модификаторов: `^{Ctrl}{"ac"}~{Ctrl}` — это Ctrl+A, Ctrl+C.
- Если символ **нельзя набрать** в текущей раскладке, используется запасной путь через буфер обмена (FR-AD-4 п.2): такой символ вставляется «как есть», зажатые модификаторы на время вставки временно отпускаются и затем восстанавливаются; «Сухой прогон» и `mkey send --dry-run` предупреждают об этом.
- Если включён CapsLock, mKey компенсирует его при наборе, чтобы результат совпадал с написанным текстом (опция `text.respect_capslock: false` по умолчанию).

**FR-DSL-2.** Устройство по умолчанию: клавиши/мышь идут на основные виртуальные клавиатуру и мышь mKey. Префикс `имя.` адресует конкретное устройство: виртуальное (`pad2.South`) или физическое по его метке/авто-ID (`Sega.Start`, `UnKey.001`). Отправка на физическое устройство идёт через его passthrough-клон (FR-DEV-3).
**FR-DSL-3.** Парсер выдаёт понятные ошибки с позицией: `строка 1, символ 14: неизвестная клавиша "Mous0" — возможно, вы имели в виду "Mouse0"?` (подсказки по расстоянию Левенштейна).
**FR-DSL-4.** Двусторонняя конвертация: DSL ⇄ AST ⇄ блоки конструктора без потерь для всего, что выразимо в DSL. Есть форматтер (канонический вид).
**FR-DSL-5.** В конце выполнения последовательности (или при её отмене) всё, что она зажала и не отпустила явно, **отпускается автоматически**, если только последовательность не завершилась намеренным `^{...}` в режиме `keep_held: true`.

### 5.2 Модель проекта: события, триггеры, условия, действия

**FR-EV-1. Лист событий.** Проект — упорядоченный список событий. Событие:

```
Событие = { имя, включено, триггеры[], условия[], действия[], политика_запуска, группа }
```

Событие срабатывает, если сработал **любой** из триггеров и выполнены **все** условия (в v1 — логическое И; ИЛИ — через «группу условий» `any:`).

**FR-EV-2. Триггеры (v1):**

| Тип | Параметры | Примечание |
|---|---|---|
| `hotkey` | `keys` (DSL-аккорд, напр. `{Ctrl+Alt+M}`), `on`: `press` \| `release` \| `hold` (≥N мс) \| `double` (двойное нажатие) \| `toggle`, `consume` (блокировать исходное нажатие), `device` (необязательно — только с этого устройства) | см. §5.4 |
| `sequence` | `keys` (`{G}{G}`), `within_ms` | последовательность нажатий, как в vim |
| `hotstring` | `text` (`btw`), `replace` (текст/действия), `end_chars` | набранная строка (аналог `::btw::` в AHK) |
| `window` | `title` (regex), `app_id`/`wm_class` (regex), `on`: `activated` \| `deactivated` \| `opened` \| `closed` | через адаптер |
| `pixel` | `x`, `y`, `color` (`#rrggbb`), `tolerance` (0–255, по каналам), `interval_ms` (≥16), `on`: `match` (фронт) \| `mismatch` \| `while` | через адаптер |
| `device` | `match` (метка/vid:pid/имя), `on`: `connected` \| `disconnected` | |
| `timer` | `every_ms` \| `cron` \| `after_ms` (от старта) | |
| `startup` | — | при загрузке проекта |
| `manual` | — | запуск из GUI/CLI/API/другого события |

**FR-EV-3. Условия (v1):** `window` (как триггер), `key_state` (клавиша/кнопка зажата/отпущена), `variable` (сравнение `==, !=, <, >, <=, >=`, `in`), `pixel` (разовая проверка), `toggle` (состояние toggle-триггера), `time` (интервал времени суток), `any`/`all`/`not` (группы).

**FR-EV-4. Действия (v1):**

| Действие | Описание |
|---|---|
| `send` | DSL-последовательность |
| `key_down` / `key_up` / `tap` | структурные эквиваленты для конструктора |
| `hold` | удерживать клавишу N мс |
| `pause` | пауза N мс или случайная `min..max` |
| `mouse_move` / `mouse_click` / `wheel` | мышь (абсолютно/относительно) |
| `type_text` | набрать текст |
| `gamepad` / `axis` | кнопка/ось виртуального геймпада |
| `touch` / `swipe` | тач |
| `repeat` | N раз / пока зажата клавиша триггера / пока toggle включён / пока условие истинно / бесконечно (с защитой, §7) |
| `if` / `else` | ветвление по условиям |
| `set_var` | установить/увеличить переменную (int, float, string, bool) |
| `run_event` | запустить другое событие (с ожиданием или без) |
| `play_recording` | воспроизвести запись (скорость, повторы) |
| `lua` | Lua-скрипт (инлайн или файл) |
| `shell` | bash-скрипт (инлайн или файл), таймаут |

| `enable` / `disable` | включить/выключить событие или проект |
| `stop` | остановить раннеры (текущий / все) |

**FR-EV-5. Политика повторного запуска** (если событие сработало, пока предыдущий запуск ещё идёт): `ignore` (по умолчанию), `restart`, `queue`, `parallel` (с лимитом).
**FR-EV-6. Переменные:** глобальные (на проект) и локальные (на запуск); доступны в условиях, Lua (`mkey.var.x`), bash (`MKEY_VAR_X` на чтение, `mkey var set x 1` на запись). Опция `persist: true` сохраняет значение между перезапусками.
**FR-EV-7. Профили по окнам:** у проекта может быть условие `active_when: {window: ...}` — тогда все его события активны только в этом окне (частый сценарий «макросы только для игры»).
**FR-EV-8. Горячая перезагрузка:** изменение файла проекта на диске применяется без перезапуска демона; при ошибке валидации старая версия продолжает работать, ошибка показывается в GUI/CLI/уведомлении.

### 5.3 Скрипты Lua и bash

**FR-LUA-1.** Lua 5.1 (gopher-lua). Модуль `mkey` (полное описание — `docs/lua-api.md`):

```lua
mkey.send("^{Mouse0}[500]~{Mouse0}")     -- DSL
mkey.tap("A"); mkey.down("Shift"); mkey.up("Shift")   -- имена клавиш те же, что в DSL
mkey.hold("Space", 300)
mkey.sleep(250)                           -- прерываемая пауза (учитывает отмену)
mkey.move(100, 200); mkey.move_rel(10, -5); mkey.click("Mouse1")
mkey.type("Привет")
mkey.is_down("mouse0")                    -- состояние физических клавиш
local w = mkey.window()                   -- {title=, app_id=, pid=} или nil
local r, g, b = mkey.pixel(960, 540)      -- nil, err если недоступно
local x, y = mkey.cursor()
mkey.var.counter = (mkey.var.counter or 0) + 1
mkey.notify("Готово")
mkey.run("Другое событие")
local pad = mkey.device("pad2"); pad:press("South"); pad:axis("LX", 0.5)
mkey.log("debug text")
mkey.on_stop(function() ... end)          -- очистка при отмене
```

**FR-LUA-2.** Каждый запуск — свой `LState`; отмена через контекст (все блокирующие вызовы прерываются, цикл без вызовов `mkey.*` прерывается хуком по счётчику инструкций).
**FR-LUA-3.** Стандартные библиотеки `os.execute`/`io.popen` доступны (это пользовательские скрипты), но при **импорте** чужого проекта, содержащего `lua`/`shell`, GUI показывает предупреждение со списком скриптов (§7).

**FR-SH-1.** bash-скрипты запускаются `bash -c` / файлом с окружением: `MKEY_SOCKET`, `MKEY_EVENT`, `MKEY_PROJECT`, `MKEY_VAR_*`; в `PATH` гарантированно есть `mkey`. Внутри скрипта используются команды CLI: `mkey send '^{Mouse0}'`, `mkey wait key F8`, `mkey var set x 1`, `mkey pixel 10 20`, `mkey window`.
**FR-SH-2.** Таймаут (по умолчанию 60 с, настраиваемый), stdout/stderr — в лог события; отмена события посылает SIGTERM, через 2 с — SIGKILL группе процессов.
**FR-SH-3.** Задержка одного вызова `mkey send` из bash — ≤ 5 мс (Unix-сокет, без запуска демона).

### 5.4 Горячие клавиши и перехват ввода

**FR-HK-1. Режим наблюдения (без grab):** если ни один активный хоткей не требует `consume`, mKey только читает события — исходные нажатия доходят до приложений.
**FR-HK-2. Режим перехвата (grab + passthrough):** для устройств, на которых есть `consume`-хоткеи или переназначения, mKey делает `EVIOCGRAB` и пересылает все остальные события через виртуальный клон устройства (с теми же capabilities). Цель по задержке — §6.
**FR-HK-3. Проблема зажатых модификаторов:** если хоткей `ctrl+j` отправляет `abc`, приложение увидело бы `ctrl+a`. В режиме перехвата mKey перед выполнением действий временно «отпускает» модификаторы на passthrough-устройстве и восстанавливает их после (опция события `release_modifiers: auto|always|never`, по умолчанию `auto`). В режиме наблюдения это невозможно — GUI предупреждает и предлагает включить `consume` или опцию «ждать отпускания модификаторов».
**FR-HK-4. Переназначение (remap):** простое действие-правило `remap: {from: CapsLock, to: Esc}` (1:1, выполняется прямо в passthrough-пути без раннеров); `from` может быть с конкретного устройства.
**FR-HK-5.** Toggle-хоткеи и `repeat while held` — базовые сценарии автокликера; должны работать «из коробки» по шаблону в GUI.
**FR-HK-6.** Хоткеи записи/остановки/экстренного стопа никогда не попадают в записи и не передаются в приложения.

### 5.5 Запись и воспроизведение

**FR-REC-1.** Запись с выбранных устройств (по умолчанию — все клавиатуры и мыши; тач — по выбору): все события evdev с временными метками ядра (`input_event.time`), включая multitouch protocol B (`ABS_MT_SLOT`, `ABS_MT_TRACKING_ID`, …).
**FR-REC-2.** Старт/стоп: кнопка в GUI, хоткей (по умолчанию `{Ctrl+Alt+R}`, настраивается), `mkey rec start|stop`. Обратный отсчёт перед стартом (опция). Хоткей старт/стоп из записи вырезается.
**FR-REC-3.** Формат записи — `recordings/<имя>.mkrec` (JSON Lines, сжатие zstd опционально): заголовок (устройства и их capabilities, разрешение экрана, адаптер позиции курсора) + события.
**FR-REC-4.** Воспроизведение: скорость (0.1×–10×), повторы, «сохранять оригинальные паузы» / «фиксированная пауза», «пропускать движения мыши», старт с исходной позиции курсора (если доступен `PointerLocator`). Для тача и геймпадов — через виртуальные устройства с теми же capabilities (клон).
**FR-REC-5. Мышь — честная оговорка:** evdev даёт только относительные перемещения; ускорение указателя может сделать воспроизведение неточным. Решение: если адаптер умеет читать позицию курсора (X11, KDE, GNOME-расширение, Hyprland), при записи сохраняются также абсолютные координаты, а воспроизведение идёт через **виртуальное абсолютное устройство** (tablet-like, `ABS_X/ABS_Y`, диапазон = размер экрана/всех мониторов). Иначе — относительное воспроизведение и подсказка в GUI («для точности отключите ускорение мыши»).
**FR-REC-6. Конвертация в конструктор:** запись → список действий: слияние `down+up` в `tap`/`hold`, квантование пауз (порог, напр. 10 мс), прореживание движений мыши (алгоритм Рамера—Дугласа—Пекера по траектории), удаление пауз короче порога. Результат редактируется как обычное событие.

### 5.6 Инспектор устройств и подписи кнопок

**FR-DEV-1.** Список всех устройств: имя, vid:pid, версия, `phys`, `uniq`, путь `by-id`/`by-path`, тип (клавиатура/мышь/геймпад/тач/планшет/прочее — эвристика по capabilities), поддерживаемые коды, для осей — `min/max/fuzz/flat/resolution`.
**FR-DEV-2. Авто-ID для неизвестных устройств и кнопок.** Всё, у чего нет стандартного имени mKey (устройство не распознано как обычная клавиатура/мышь/геймпад, или у известного устройства есть «лишние» коды — например, G-клавиши), получает автоматический ID:
- **устройство:** `UnKey` (первое неизвестное), затем `UnKey2`, `UnKey3`… ID присваивается при первом обнаружении и сохраняется в `devices.yaml`, привязанный к стабильному идентификатору устройства (FR-DEV-6), — после переподключения устройство остаётся тем же `UnKey2`;
- **кнопки:** `001`, `002`, … (ровно три цифры) — по возрастанию кодов evdev из capabilities устройства. Нумерация детерминирована: одинаковые модели получают одинаковые номера, нажимать кнопки для этого не нужно;
- **оси:** `Axis01`, `Axis02`… (абсолютные, включая крестовины-hat), `Rel01`… (относительные).
- **Запись в DSL:** `{UnKey001}` — кнопка 001 устройства UnKey; полная форма — `{UnKey.001}`. Для `UnKey2` и далее форматтер пишет форму с точкой (`{UnKey2.001}`); слитная `{UnKey2001}` тоже допустима (последние три цифры — всегда номер кнопки). Оси — `{UnKey.Axis01=0.5}`.
- Авто-ID работают везде, где работают обычные клавиши: хоткеи (`keys: "{UnKey001}"`), условия `key_state`, привязки, запись, Lua (`mkey.is_down("UnKey.001")`).

**FR-DEV-3. Переименование.** Устройство и каждую его кнопку/ось можно переименовать в GUI («Устройства → устройство → кнопка → Переименовать») или в `devices.yaml`. Пример: `UnKey` → `Sega`, `001` → `Start` ⇒ `{Sega.Start}`.
- Авто-ID **навсегда остаются рабочими алиасами**: старые макросы с `{UnKey001}` не ломаются; GUI и форматтер показывают текущее имя.
- Правила имён: буквы (латиница/кириллица), цифры, `_`, начинается с буквы; регистр не важен; имя устройства уникально и не совпадает с именами стандартных клавиш и виртуальных устройств; имя кнопки уникально в пределах устройства. Ошибки — понятным языком с подсказкой.
- Метки можно давать и известным устройствам (например, `{MyKeyboard.G1}`).
- **Отправка на физическое устройство** (`{Sega.Start}` в действии): приложения видят нажатие только если устройство переведено в режим перехвата — mKey скрывает оригинал (grab) и показывает системе его виртуальный клон, в который и отправляет нажатия. При первом таком макросе GUI объясняет это и включает режим по согласию.

**FR-DEV-4. Режим «Узнать кнопку»:** пользователь выбирает устройство (или «любое»), нажимает кнопку — GUI показывает устройство, её имя/авто-ID (`UnKey.003`), тип/код события (`EV_KEY BTN_TRIGGER_HAPPY3 = 0x2c2`), значение; для осей — живой индикатор; рядом — кнопка «Переименовать».
**FR-DEV-5. Мастер разметки:** «Нажимайте по очереди все кнопки устройства» — mKey подсвечивает найденные кнопки и предлагает дать каждой имя (можно пропустить — останется авто-ID). Результат можно экспортировать как **профиль устройства** (FR-PLG-8) и поделиться им.
**FR-DEV-6. Стабильная идентификация** устройства между перезагрузками: `vid:pid:version` + имя + `uniq` (если есть) + как запасной вариант `by-path`. Если подключено два одинаковых устройства без `uniq`, они различаются по порту USB — GUI предупреждает, что при смене портов они поменяются местами.
**FR-DEV-7. Профили устройств:** если устройство совпадает со встроенным или установленным профилем (`profiles/devices/*.yaml`), имена кнопок подставляются автоматически; пользовательские метки имеют приоритет.
**FR-DEV-8.** Живой монитор событий (аналог `evtest`) с фильтрами и экспортом.
**FR-DEV-9.** Устройства, у которых кнопки не видны через evdev (часть HID-кнопок, «игровые» клавиши без драйвера) — в v1 только диагностика и подсказка; чтение hidraw — бэклог (кандидат в плагин).

Пример `devices.yaml`:
```yaml
version: 1
devices:
  - auto_id: UnKey                      # авто-ID, остаётся алиасом навсегда
    name: Sega                          # имя, заданное пользователем
    match: { vid: "0079", pid: "0011", name: "USB Gamepad", by_path: "pci-0000:00:14.0-usb-0:2:1.0" }
    buttons:
      "001": { code: BTN_TRIGGER, name: A }
      "002": { code: BTN_THUMB,   name: B }
      "010": { code: BTN_BASE4,   name: Start }
    axes:
      Axis01: { code: ABS_X, name: DPadX }
```

### 5.7 Виртуальные устройства и привязки

**FR-VD-1. Шаблоны:** клавиатура, мышь (относительная), абсолютный указатель, тач-экран (`INPUT_PROP_DIRECT`, MT protocol B, до 10 касаний), геймпад **Xbox 360** (vid:pid `045e:028e` — распознаётся SDL/Steam/играми), **DualShock 4**-подобный, универсальный джойстик, **пользовательский** (произвольный набор кодов и осей с диапазонами).
**FR-VD-2.** Пользователь даёт устройству короткое имя (`pad2`), которое используется в DSL/Lua. Имя в системе — `mKey <имя>`. Устройства из конфигурации создаются при старте демона и живут постоянно (композитору нужно 100–500 мс, чтобы подхватить новое устройство — создавать «на лету» перед каждым нажатием нельзя).
**FR-VD-3. Привязки (bindings):** декларативные правила «физический вход → виртуальный выход» без написания событий:
- кнопка → кнопка (`kbd:W` → `pad2.DPadUp`);
- клавиши → ось (`w/s` → `pad2.ly` −1/+1, с опциональным сглаживанием);
- ось → ось (инверсия, мёртвая зона, кривая, масштаб);
- мышь → стик (чувствительность, возврат к центру);
- ось → кнопки (порог).
Привязки работают в passthrough-пути (минимальная задержка). Исходное устройство можно «спрятать» от системы (grab), чтобы приложения видели только виртуальное.
**FR-VD-4. Сценарий «второй геймпад»:** в GUI мастер «Создать второй геймпад из клавиатуры/мыши» с готовой раскладкой.
**FR-VD-5.** Force feedback (вибрация) виртуальных геймпадов — принимать запросы, опционально пробрасывать на физический геймпад; в v1 — принимать и игнорировать корректно (не ломать игры).

### 5.8 Десктоп-адаптеры: окна, пиксели, курсор, раскладка

Контракты в `internal/contracts` (реализации — модули `internal/desktop/<adapter>`):

```go
type WindowTracker interface { Active(ctx) (Window, error); Subscribe(ctx) (<-chan WindowEvent, error) }
type PixelReader   interface { Pixels(ctx, pts []image.Point) ([]color.RGBA, error) }
type PointerLocator interface { Position(ctx) (image.Point, error) }
type LayoutProvider interface { Current(ctx) (Layout, error) } // xkb layout+variant+group
```

Каждый адаптер сообщает `Capabilities()`; `session` выбирает лучший доступный адаптер для каждой функции; `mkey doctor` и GUI показывают таблицу.

**FR-AD-1. Матрица поддержки (целевая для v1):**

| Окружение | Активное окно | Пиксель | Позиция курсора | Раскладка |
|---|---|---|---|---|
| **X11** (любой WM) | EWMH `_NET_ACTIVE_WINDOW` (xgb), события PropertyNotify | `GetImage` 1×1 (xgb) | `QueryPointer` | XKB |
| **GNOME (Wayland)** | собственное GNOME Shell-расширение `mkey@mkey` → D-Bus `io.mkey.Shell` (сигнал смены фокуса) | расширение: `Shell.Screenshot.pick_color` | расширение: `global.get_pointer()` | расширение / gsettings `input-sources` |
| **KDE Plasma 6 (Wayland)** | KWin-скрипт (загружается через D-Bus `org.kde.KWin /Scripting`), колбэки в наш D-Bus-сервис | KWin `org.kde.KWin.ScreenShot2` (нужен .desktop с `X-KDE-DBUS-Restricted-Interfaces`) | KWin-скрипт `workspace.cursorPos` | D-Bus `org.kde.keyboard /Layouts` |
| **Sway** | IPC (`SWAYSOCK`), подписка на `window` | `wlr-screencopy` / `ext-image-copy-capture` | нет (только отслеживаемая mKey) | IPC `get_inputs` |
| **Hyprland** | socket2 `activewindow` | `wlr-screencopy` | `hyprctl cursorpos` (socket) | `hyprctl devices` |
| **Другие wlroots** (labwc, river, Wayfire…) | `wlr-foreign-toplevel-management` | `wlr-screencopy` | нет | нет → US + запасной путь |
| **Прочие Wayland** | `ext-foreign-toplevel-list` (без признака фокуса — только opened/closed) | xdg-desktop-portal Screenshot (медленно, может спросить разрешение) | нет | нет |

Допустимо реализовывать построчно (см. фазу 8). Если возможность недоступна — **явное сообщение** пользователю с объяснением и советом, а не молчаливый отказ.

**FR-AD-2.** Расширение GNOME и KWin-скрипт — часть репозитория (`extensions/`), ставятся только по согласию пользователя. Для GNOME на Wayland новое расширение обычно активируется только после перелогина — mKey обязан предупредить об этом.
**FR-AD-3.** Пиксельные запросы батчатся: все пиксельные триггеры одного тика — один захват. Минимальный интервал опроса — 16 мс; если адаптер медленный (portal), интервал автоматически повышается, пользователь видит фактический.
**FR-AD-4. Набор текста (`type_text`)**: evdev оперирует кодами физических клавиш, поэтому для текста нужна раскладка:
1. v1: символы, доступные в текущей раскладке (через `LayoutProvider` + встроенные таблицы популярных раскладок `us, ru, ua, by, de, fr, es, it, pl, cz, tr`, с учётом Shift/AltGr) печатаются клавишами; при необходимости mKey временно переключает раскладку (где адаптер это умеет);
2. запасной путь для остальных символов — через буфер обмена (`wl-copy`/`xclip`, если установлены, или встроенная реализация) + `Ctrl+V` (в терминалах — `Ctrl+Shift+V`, определяется по активному окну, где есть адаптер), с восстановлением старого содержимого буфера; зажатые пользователем модификаторы на время вставки отпускаются;
   Правило взаимодействия набора с зажатыми через `^{...}` модификаторами — §5.1 «Набор текста».
3. v2: полноценный разбор xkb keymap (keymap можно получить как Wayland-клиент через `wl_keyboard.keymap`).

### 5.9 Веб-интерфейс (GUI) и конструктор

**FR-UI-1. Разделы:**
1. **Главная** — статус демона, активные проекты/события, запущенные раннеры (с кнопкой «Стоп»), кнопка «Экстренная остановка», предупреждения диагностики.
2. **Проекты** — список, вкл/выкл, импорт/экспорт, шаблоны («Автокликер», «Remap CapsLock→Esc», «Второй геймпад», «Повтор записанного», «Реакция на красный пиксель»).
3. **Редактор событий (конструктор)** — см. ниже.
4. **Запись** — старт/стоп, список записей, просмотр таймлайна, конвертация в событие.
5. **Устройства** — инспектор, «Узнать кнопку», метки.
6. **Виртуальные устройства и привязки.**

8. **Настройки** — хоткеи записи/стопа, интервалы по умолчанию, язык, автозапуск, адаптеры, **удаление программы**.
9. **Диагностика** — вывод `doctor` понятным языком, кнопки «Исправить».
10. **Мастер первого запуска** (§5.11).

**FR-UI-2. Лист событий (в духе Construct 3):** каждое событие — строка из двух колонок: слева **«Когда»** (триггеры + условия), справа **«Делать»** (действия). Строки можно перетаскивать, сворачивать, группировать, отключать, дублировать. У события есть переключатель вкл/выкл и индикатор «сейчас выполняется».
**FR-UI-3. Блоки действий:** палитра блоков слева (категории: Клавиатура, Мышь, Геймпад, Тач, Время, Логика, Переменные, Скрипты, Система). Блоки перетаскиваются в колонку «Делать», вкладываются в `Повтор`/`Если`. Параметры редактируются прямо в блоке (клавиша — кнопкой «Нажмите клавишу…», которая ловит реальное нажатие через API; время — поле с мс; координаты — кнопкой «Указать на экране» там, где есть `PointerLocator`).
**FR-UI-4. Режим DSL:** любую последовательность блоков можно переключить в текстовый вид (DSL) и обратно (FR-DSL-4). Ошибки подсвечиваются в строке.
**FR-UI-5. Выбор триггера** — мастер с понятными формулировками: «Когда я нажимаю…», «Когда я удерживаю…», «Когда открывается окно…», «Когда в точке экрана цвет…», «Каждые N секунд», «Когда подключено устройство…». Для пикселя — пипетка (где поддерживается), для окна — выбор из списка открытых/последних окон.
**FR-UI-6. Тест:** кнопка «Запустить сейчас» и «Сухой прогон» (показывает таймлайн действий без реального ввода).
**FR-UI-7.** Все изменения сохраняются в YAML через API; конфликт с ручной правкой файла (файл изменился на диске) — диалог «перезагрузить / перезаписать».
**FR-UI-8.** Интерфейс локализован: **русский и английский** с первого дня (i18n-ключи, никаких строк в разметке). Тексты — простым языком, без жаргона («устройство ввода», а не «evdev-нода»; технические детали — под спойлером «Подробнее»).
**FR-UI-9.** Адаптивная вёрстка, светлая/тёмная тема (системная по умолчанию).
**FR-UI-10.** Открытие GUI: `mkey gui` / ярлык в меню / иконка в трее (StatusNotifierItem) → `xdg-open http://127.0.0.1:<port>/?t=<одноразовый-токен>`.

**Стек фронтенда:** Svelte 5 + TypeScript + Vite; drag-and-drop — SortableJS (вложенные списки, клонирование из палитры); редактор кода — CodeMirror 6; сборка в `web/dist`, встраивание через `go:embed`. Без тяжёлых UI-фреймворков; собственный небольшой набор компонентов.

### 5.10 CLI

Один бинарник `mkey`, библиотека `spf13/cobra`. Все команды, кроме `daemon`, `setup`, `uninstall`, `privileged`, — клиенты API через Unix-сокет. Вывод: человекочитаемый по умолчанию, `--json` для скриптов. Коды возврата документированы.

```
mkey                       # без аргументов: если не установлен → мастер установки; иначе → открыть GUI
mkey daemon                # запустить демон (обычно запускает systemd --user)
mkey gui                   # открыть веб-интерфейс
mkey status                # состояние демона, проектов, раннеров
mkey doctor [--fix]        # диагностика окружения и прав
mkey setup                 # мастер первичной настройки в терминале (альтернатива GUI)
mkey send '<dsl>'          # выполнить последовательность
mkey run <событие|файл.lua|файл.sh>
mkey stop [--all]          # остановить раннеры; `mkey panic` — экстренная остановка
mkey project list|enable|disable|import|export|validate <...>
mkey event list|enable|disable|run <...>
mkey rec start|stop|list|play|convert <...>
mkey devices list|inspect|watch|label <...>
mkey vdev list|create|remove <...>   # напр. mkey vdev create pad2 --template xbox360
mkey var get|set <имя> [значение]
mkey wait key <клавиша> | window <regex> | pixel <x> <y> <#цвет>   # для bash-скриптов
mkey window | cursor | pixel <x> <y>
mkey config get|set|edit
mkey logs [-f]
mkey uninstall [--keep-config] [--yes]
mkey version
```

**FR-CLI-1.** Если демон не запущен, клиентская команда сообщает об этом и предлагает `mkey daemon`/запуск сервиса (или запускает сам с флагом `--autostart-daemon`).
**FR-CLI-2.** Автодополнение для bash/zsh/fish (`mkey completion`).

### 5.11 Установка, права, первый запуск, удаление

**Принцип:** пользователь ничего не делает в терминале. Любое изменение системы — только после объяснения простым языком и явного согласия. Всё, что mKey ставит, записывается в манифест.

**FR-INST-1. Способы поставки:**
1. **Основной:** один исполняемый файл `mkey` (x86_64 и aarch64) из релизов. Первый запуск (`./mkey` или двойной клик, если ФМ разрешает) → копирует себя в `~/.local/bin/mkey`, создаёт `.desktop`-ярлык, запускает демон, открывает мастер в браузере.
2. Пакеты `.deb`/`.rpm`/AUR, а также `xbps` (Void) и `apk` (Alpine) (goreleaser + nfpm) — фаза 10.
3. **Flatpak/Snap — не поддерживаем**: песочница несовместима с прямым доступом к `/dev/input` и установкой udev-правил (ADR).

**FR-INST-2. Мастер первого запуска** (GUI, дублируется в `mkey setup`):
1. **Приветствие** — что умеет mKey, что потребуется.
2. **Проверка системы** (`doctor`): тип сессии, композитор, init-система, systemd-logind/elogind, менеджер устройств (systemd-udevd/eudev/mdev), наличие модуля `uinput`, доступ к `/dev/uinput` и `/dev/input/event*`, polkit-агент, `sudo`/`doas`, `XDG_RUNTIME_DIR`, версия ядра; результат — зелёные/жёлтые/красные пункты человеческим языком.
3. **Права доступа** — пример текста:
   > «Чтобы mKey мог видеть нажатия клавиш и нажимать клавиши за вас, системе нужно одно разрешение. Мы создадим файл правил `/etc/udev/rules.d/70-mkey.rules` и включим системный модуль виртуального ввода. Сейчас появится окно с запросом пароля администратора.
   > Важно: после этого программы, запущенные от вашего имени, смогут читать нажатия клавиш. Так работают все программы такого рода. [Подробнее]
   > [Разрешить] [Отмена]»

   Выполняется `pkexec /home/<user>/.local/bin/mkey privileged install-rules` (или другой бэкенд повышения прав, FR-INST-7). Команда `privileged` принимает **только фиксированный набор подкоманд без произвольных путей и аргументов**, содержимое правил зашито в бинарник:
   ```
   # /etc/udev/rules.d/70-mkey.rules  (managed by mKey)
   KERNEL=="uinput", SUBSYSTEM=="misc", TAG+="uaccess", OPTIONS+="static_node=uinput"
   SUBSYSTEM=="input", KERNEL=="event*", TAG+="uaccess"
   ```
   + файл автозагрузки модуля `uinput` (путь выбирает платформенный бэкенд, FR-INST-7; для systemd — `/etc/modules-load.d/mkey.conf`), затем `modprobe uinput`, `udevadm control --reload`, `udevadm trigger --subsystem-match=input --subsystem-match=misc`. Номер `70-` обязателен: тег `uaccess` должен быть выставлен до `73-seat-late.rules`.
   **Запасной путь** (нет logind / uaccess не сработал — проверяется фактическим открытием устройств): добавить пользователя в группу `input` + правило `GROUP="input", MODE="0660"` для uinput; предупредить, что нужен перелогин.
   **Нет polkit-агента:** открыть окно терминала с `sudo`/`doas` и пояснением; если и это невозможно — показать одну команду для копирования.
4. **Интеграция с рабочим столом** (по ситуации): GNOME — поставить и включить расширение (с предупреждением про перелогин); KDE — KWin-скрипт и .desktop для ScreenShot2; предложить установить `wl-clipboard`, если нужен (через пакетный менеджер дистрибутива — бэкенды apt, dnf, pacman, zypper, xbps, apk, emerge; определяется по `/etc/os-release`, выполняется через бэкенд повышения прав после согласия).
5. **Автозапуск** — через бэкенд init-системы (FR-INST-7): systemd `--user` unit `~/.config/systemd/user/mkey.service` (`Restart=on-failure`), либо пользовательский сервис runit/dinit/OpenRC, где он доступен, либо XDG autostart `.desktop`, либо (для Sway, Hyprland, river и др. композиторов без XDG autostart) строка запуска в конфиге композитора в помеченном блоке `# >>> mKey >>>` … `# <<< mKey <<<` — с согласия, с записью в манифест и удалением при деинсталляции.
6. **Проверка** — «Нажмите любую клавишу» (проверка чтения) и «Сейчас mKey напечатает букву» в поле ввода (проверка uinput).
7. **Готово** — предложить шаблоны.

**FR-INST-3. Повторная диагностика:** при каждом старте демон выполняет быструю проверку; при проблемах (например, после обновления системы правило удалено) — уведомление и пункт «Исправить».
**FR-INST-4. Манифест:** `~/.local/share/mkey/install-manifest.json` — список всех созданных файлов (пользовательских и системных), изменений групп, установленных пакетов (с пометкой «установлено mKey»), версий.
**FR-INST-5. Удаление** (GUI «Настройки → Удалить mKey» или `mkey uninstall`):
- диалог: **«Удалить полностью»** / **«Удалить, но сохранить настройки и макросы»**; отдельно — галочки «удалить пакеты, которые ставил mKey» (по умолчанию выкл.) и «вернуть группу input» (если меняли);
- порядок: остановить раннеры и отпустить всё → остановить и отключить сервис → удалить расширения/скрипты → через один запрос pkexec удалить системные файлы (`privileged uninstall-rules`) → удалить пользовательские файлы по манифесту → удалить бинарник последним;
- при сохранении настроек остаются `~/.config/mkey/` и `~/.local/share/mkey/recordings/`; при повторной установке они подхватываются автоматически;
- в конце — отчёт, что удалено; если что-то не удалось — список с причинами и ручными командами.
**FR-INST-7. Системы без systemd — полная поддержка** через платформенные бэкенды (`internal/platform`, точки расширения §4.3):

| Задача | systemd | Без systemd |
|---|---|---|
| Определение init | `/run/systemd/system` | OpenRC (`/run/openrc`), runit (`/run/runit`), dinit, s6, sysvinit — по PID 1 и маркерам |
| Доступ к устройствам | udev `uaccess` | `uaccess` при elogind + systemd-udevd; иначе группа `input` (eudev); для `mdev`/`mdevd` (Alpine) — строка в `/etc/mdev.conf` |
| Автозагрузка `uinput` | `/etc/modules-load.d/mkey.conf` | OpenRC — `modules-load.d` или `/etc/conf.d/modules`; Void (runit) — `modules-load.d`; Alpine — `/etc/modules` |
| Автозапуск демона | systemd `--user` | пользовательские сервисы (turnstile/runit, dinit, OpenRC user services — где есть), иначе XDG autostart или конфиг композитора |
| Повышение прав | pkexec | pkexec, если есть polkit; иначе `sudo`/`doas` в окне терминала |
| `XDG_RUNTIME_DIR` | всегда есть | если нет — `/tmp/mkey-$UID` с проверкой владельца и прав 0700 |

Все пути и команды каждого бэкенда записываются в манифест, чтобы деинсталляция работала одинаково. Новые init-системы и дистрибутивы добавляются новым бэкендом или плагином без правки остального кода.

**FR-INST-6. Обновление:** проверка новой версии (выключаемая, по умолчанию спрашивается в мастере), замена бинарника, миграция схемы конфигов с бэкапом.

### 5.12 Плагины

**FR-PLG-1. Виды плагинов:**
1. **Lua-плагин** — папка с `plugin.yaml` и `main.lua`. Регистрирует действия, условия, триггеры, команды DSL и функции Lua API (`mkey.register_action{...}` и т.п.). Выполняется внутри демона в собственном `LState`. Для простых расширений.
2. **Плагин-процесс** — любой исполняемый файл (Go, Python, Rust, bash…). Общается с демоном по **JSON-RPC 2.0 через stdin/stdout** (одно JSON-сообщение на строку; логи — в stderr). Может предоставлять всё из таблицы точек расширения §4.3, включая десктоп-адаптеры, init-системы, пакетные менеджеры — то есть **поддержку новых систем и окружений**.
3. **Плагин-данные** — только YAML: профили устройств, шаблоны виртуальных устройств, шаблоны проектов. Без кода.

**FR-PLG-2. Манифест `plugin.yaml`:**
```yaml
id: io.example.http-actions
name: { ru: "HTTP-действия", en: "HTTP actions" }
version: 1.2.0
plugin_api: 1                 # мажорная версия API плагинов
min_mkey: 1.0.0
kind: process                 # lua | process | data
entry: ./http-actions         # исполняемый файл или main.lua
platforms: [x11, wayland]     # необязательно: сессии/композиторы/init-системы
provides:
  actions: [http_request]
  triggers: [http_webhook]
permissions: [net, vars.write]  # показываются пользователю при установке
```

**FR-PLG-3. Жизненный цикл:** поиск в `~/.local/share/mkey/plugins/` и `/usr/share/mkey/plugins/` → проверка манифеста и версии API → запуск → рукопожатие (`initialize`: версии, capabilities) → регистрация типов в реестрах → пинги здоровья → остановка (`shutdown`). Упавший процесс перезапускается с нарастающей паузой; после 3 падений за минуту плагин отключается, пользователь получает уведомление.
**FR-PLG-4. Установка и управление:** GUI «Плагины» (установка из папки/архива, список, вкл/выкл, разрешения, логи, удаление) и CLI `mkey plugin list|install|remove|enable|disable|logs`. Новый плагин по умолчанию **выключен**, пока пользователь не просмотрит разрешения и не включит его. Установленные файлы плагина учитываются в манифесте (FR-INST-4).
**FR-PLG-5. Разрешения:** демон проверяет каждый вызов API плагина на соответствие объявленным `permissions` (`input.read`, `input.grab`, `output.send`, `desktop.window`, `desktop.pixel`, `vars.read`, `vars.write`, `projects.write`, `net`, `exec`). Честная оговорка для пользователя: плагин-процесс работает с правами пользователя и не является песочницей на уровне ОС — установка плагина означает доверие автору.
**FR-PLG-6. Изоляция:** ошибка, зависание или падение плагина не роняют демон; у вызовов есть таймауты (проверка условия — 2 с по умолчанию, действия — отменяемые через `$/cancel`).
**FR-PLG-7. Производительность:** плагины не участвуют в «горячем» passthrough-пути (FR-HK-2); их триггеры приходят в движок как события.
**FR-PLG-8. Профили устройств** как плагины-данные: имена кнопок для известных моделей, делятся экспортом из мастера разметки (FR-DEV-5).
**FR-PLG-9. SDK и примеры:** `pkg/pluginsdk` (Go, публичный пакет) + `pkg/pluginsdk/plugintest` (тестовый хост для проверки соответствия протоколу); `docs/plugins.md` — протокол, манифест, разрешения, методы; примеры в `examples/plugins/`: `go-hello-action`, `lua-counter`, `python-webhook` (доказывает независимость от языка).

## 7. Безопасность и защита от «зависания» ввода

- **SEC-1. Экстренная остановка:** одновременное нажатие `Esc + Backspace + Enter` (как в keyd; настраивается) обрабатывается на самом нижнем уровне чтения, до любых проектов: останавливает все раннеры, отпускает все зажатые виртуальные клавиши, **снимает все grab'ы**. Дублируется: `mkey panic`, кнопка в GUI, пункт в трее.
- **SEC-2.** При остановке/отмене раннера и при завершении демона (SIGTERM/SIGINT) — отпустить всё зажатое на всех виртуальных устройствах. При падении процесса ядро само освобождает grab и уничтожает uinput-устройства (дескрипторы закрываются) — физический ввод восстанавливается. Это нужно проверить интеграционным тестом.
- **SEC-3. Watchdog grab'а:** если поток чтения grabbed-устройства не обрабатывает события > 500 мс, grab снимается автоматически.
- **SEC-4.** Бесконечные циклы: `repeat` без условия выхода требует явного подтверждения в GUI; Lua-хук по инструкциям; глобальный лимит скорости выдачи событий (по умолчанию 2000 событий/с на устройство, настраивается).
- **SEC-5. Веб-API:** слушает только `127.0.0.1`; авторизация — токен из `$XDG_RUNTIME_DIR/mkey/token` (0600) → при первом открытии обменивается на HttpOnly SameSite=Strict cookie; проверка заголовков `Host` (защита от DNS rebinding) и `Origin` (CSRF), WebSocket — с той же проверкой. Unix-сокет — `$XDG_RUNTIME_DIR/mkey/mkey.sock`, права 0600.
- **SEC-6.** `mkey privileged` — только белый список подкоманд, никаких путей/аргументов от пользователя, никакого выполнения шаблонов; содержимое системных файлов зашито в бинарник.
- **SEC-7.** Импорт проектов с `lua`/`shell`/`run` — предупреждение с показом кода до включения; импортированный проект по умолчанию выключен.
- **SEC-8.** В документации — нейтральное предупреждение: некоторые онлайн-игры/античиты могут считать виртуальный ввод нарушением правил; ответственность на пользователе.

## 8. Хранение данных и форматы файлов

Каталоги по XDG:

```
~/.config/mkey/
  config.yaml              # глобальные настройки
  devices.yaml             # метки устройств и кнопок
  vdevices.yaml            # виртуальные устройства и привязки
  projects/*.mkey.yaml     # проекты
  scripts/*.lua|*.sh       # общие скрипты
~/.local/share/mkey/
  recordings/*.mkrec
  plugins/<id>/            # установленные плагины (plugin.yaml + файлы)
  install-manifest.json
  backups/                 # бэкапы перед миграциями
~/.local/state/mkey/       # логи, персистентные переменные (vars.json)
$XDG_RUNTIME_DIR/mkey/     # mkey.sock, token, pid
```

**Пример проекта** (`projects/games.mkey.yaml`):

```yaml
version: 1
name: "Игры"
enabled: true
active_when:
  window: { title: "(?i)minecraft" }
variables:
  clicks: { type: int, value: 0, persist: true }
events:
  - id: autoclick
    name: "Автокликер на F8"
    trigger:
      type: hotkey
      keys: "{F8}"
      on: toggle
      consume: true
    actions:
      - repeat:
          while: toggled
          do:
            - send: "{Mouse0}[50]"
            - set_var: { name: clicks, add: 1 }

  - id: red_alert
    name: "Прыжок, если в центре красный"
    trigger:
      type: pixel
      x: 960
      y: 540
      color: "#ff0000"
      tolerance: 20
      interval_ms: 50
      on: match
    actions:
      - send: "{Space}"
      - lua: |
          mkey.notify("Красный пиксель! Всего кликов: " .. mkey.var.clicks)

  - id: long_hold
    name: "Удержание ЛКМ"
    trigger: { type: hotkey, keys: "{Ctrl+Alt+H}", consume: true }
    actions:
      - send: "^{Mouse0}[1500]~{Mouse0}"
```

**Пример `vdevices.yaml`:**

```yaml
version: 1
devices:
  - name: pad2
    template: xbox360
bindings:
  - device: pad2
    source: { match: "vid:046d pid:c52b" }     # или метка из devices.yaml
    hide_source: false
    map:
      - { from: W, to: LY, value: -1 }
      - { from: S, to: LY, value: 1 }
      - { from: A, to: LX, value: -1 }
      - { from: D, to: LX, value: 1 }
      - { from: Space, to: South }
```

**JSON Schema** для всех YAML-файлов генерируется из Go-структур (`docs/schema/*.json`) — для валидации, автодополнения в редакторах и для GUI.

## 9. API

REST + WebSocket, префикс `/api/v1`, JSON. Полная спецификация — `docs/api.md` (OpenAPI 3.1 в `docs/openapi.yaml`, поддерживается вместе с кодом).

Основные ресурсы:

```
GET  /status                       GET/PUT /config
GET  /doctor      POST /doctor/fix/{check}
GET/POST /projects   GET/PUT/DELETE /projects/{id}   POST /projects/{id}/enable|disable|validate
POST /events/{project}/{event}/run   POST /runners/stop   POST /panic
POST /send          {dsl}          POST /dsl/parse {text} → AST | ошибки    POST /dsl/format
GET  /devices       GET /devices/{id}   PUT /devices/{id}/labels
GET/POST /vdevices  DELETE /vdevices/{name}
POST /recordings/start|stop   GET /recordings   POST /recordings/{id}/play|convert
GET  /desktop/window | /desktop/cursor | /desktop/pixel?x=&y= | /desktop/capabilities
GET/PUT /vars/{name}
GET  /registry                     # все зарегистрированные типы с метаданными и JSON Schema (для конструктора)
GET/POST /plugins   POST /plugins/{id}/enable|disable   DELETE /plugins/{id}   GET /plugins/{id}/logs
POST /setup/...     POST /uninstall
WS   /ws/events     # поток: статус раннеров, логи, изменения файлов, срабатывания
WS   /ws/input      # живые события устройств (инспектор, «Нажмите клавишу…»)
```

Ошибки — единый формат `{ "error": { "code": "dsl.unknown_key", "message": "...", "details": {...} } }`; `message` локализуется по `Accept-Language`.

**Отказались (с причинами):**

| Решение | Почему нет |
|---|---|
| ydotool | обёртка над uinput с собственным демоном и root; мы пишем в uinput напрямую |
| keyd, input-remapper, kmonad | системные демоны с собственным grab'ом — конфликт с нашим; используем как референс идей (keyd — panic-комбинация, input-remapper — UX маппинга) |
| xdotool / XTest | только X11 |
| libei / RemoteDesktop portal | не во всех композиторах, требует интерактивного разрешения; допустимо как опциональный бэкенд в будущем (бэклог) |
| Electron/Tauri | лишний вес/зависимости; веб-интерфейс в браузере достаточно |
| Flatpak/Snap | песочница несовместима с доступом к устройствам |
| Go `plugin` (.so) | требует точного совпадения версии Go и всех зависимостей, cgo, нельзя выгрузить, только Go |
| `hashicorp/go-plugin` (gRPC) | тяжёлый, неудобен для плагинов не на Go; нам хватает JSON-RPC 2.0 на `encoding/json` |
| cgo в ядре (libudev, libxkbcommon, PipeWire) | ломает «один статический бинарник»; допускается только в опциональных модулях за build-тегом |

## 12. Тестирование

- **Unit** (`go test ./...`, без прав и без устройств): DSL (табличные тесты + fuzz `FuzzParse`), движок на фейковых `input.Source`/`output.Sink`/`desktop.*` с виртуальными часами, hotkey-матчер, recorder-конвертация, store/миграции, i18n (все ключи есть в ru и en).
- **Golden-тесты** DSL: `testdata/dsl/*.mk` → ожидаемый AST/поток событий.
- **Интеграционные** (`//go:build integration`, нужен `/dev/uinput`): создание виртуальных устройств, чтение собственных событий через evdev, grab/ungrab, отпускание при падении процесса (дочерний процесс + `kill -9`), passthrough-задержка (бенчмарк). В CI — GitHub Actions ubuntu-runner с `sudo modprobe uinput`.
- **Адаптеры:** X11 — Xvfb + простой WM; wlroots — headless sway (`WLR_BACKENDS=headless`); GNOME/KDE — ручной чек-лист (`docs/manual-test-checklist.md`) + по возможности VM-скрипты.
- **GUI:** Vitest (компоненты, конвертация блоки⇄DSL), Playwright против демона с фейковыми бэкендами (`mkey daemon --fake-backends`).
- **Модульность:** тест-матрица «демон стартует и проходит smoke-тест при отключении каждого необязательного модуля» (`internal/app`); архитектурный тест `internal/archtest` в CI.
- **Плагины:** `plugintest` — проверка соответствия протоколу; e2e с примерами из `examples/plugins/` (включая падение и перезапуск плагина).
- **Платформы:** установка/удаление и smoke-тест в контейнерах/VM для каждой init-системы из NFR-6 (Void, Artix, Alpine, Devuan) и для systemd-дистрибутивов.
- **Линтеры:** `golangci-lint` (включая `revive` с правилами `exported`/`package-comments`, `godot`, `misspell`), `go vet`, `staticcheck`; фронт — `eslint`, `svelte-check`, `prettier`.
- **Покрытие:** `dsl`, `engine`, `hotkeys`, `keys`, `store` — ≥ 80 %.

## 14. Процесс: ADR, статусы, открытые вопросы

- **ADR** (`docs/adr/NNNN-название.md`, формат: Контекст / Решение / Последствия / Альтернативы) — для любого решения, меняющего архитектуру, добавляющего зависимость, меняющего формат файлов или грамматику DSL.
- **Изменение ТЗ** — правка этого файла в том же PR, что и ADR.
- **Статусы задач** — чекбоксы в §13.

**Открытые вопросы (решить до/в указанной фазе):**

1. Хостинг репозитория и итоговый путь Go-модуля — до публикации (сейчас локально, модуль `mkey`).

**Решено владельцем (2026-09-29):**
- Клавиши называются только явными именами (`{Ctrl}`, `{Shift}`); `^` — зажать, `~` — отпустить, `{Key}` — нажать, `{Key 500}` — удержание, `[250]` — пауза, `{"..."}` — текст с JSON-экранированиями; зажатые модификаторы действуют на набираемый текст (§5.1).
- Экстренная остановка — `Esc+Backspace+Enter` (настраивается).
- Лицензия — MIT.
- Дистрибутивы без systemd (Void, Alpine, Artix, Devuan, Gentoo/OpenRC, Chimera) — **полная поддержка** через платформенные бэкенды (FR-INST-7), входят в обязательную матрицу NFR-6.
- Неизвестные устройства и кнопки получают авто-ID `{UnKey001}` с возможностью переименования (§5.6).
- Программа модульная и расширяемая, с поддержкой плагинов (§4.3, §5.12).
- Код подробно комментируется: каждый логический блок — комментарий «что он делает» (D15, `AGENTS.md` §6). **Комментарии в коде — на русском.**
- Репозиторий пока только локальный; путь Go-модуля — `mkey` (заменить на полный путь при публикации).
