# Стиль кода и комментирования mKey

Решение: [ADR-0015](adr/0015-detailed-comments-russian.md). Краткая версия — в `AGENTS.md` §6.

## Главное правило

Код должен читаться человеком, который видит его впервые. Поэтому комментарии обязательны
и пишутся **на русском**. Идентификаторы, строки логов, коды ошибок и сообщения коммитов —
на английском.

## Что комментировать

1. **Пакет** — файл `doc.go` с комментарием `// Package <имя> …`: назначение, основные типы,
   связь с другими модулями, как расширять.
2. **Каждое объявление** — тип, функция, метод, константа или группа констант, переменная
   уровня пакета (экспортируемые и нет). Комментарий начинается с имени идентификатора
   (конвенция Go, её проверяет `revive`) и заканчивается точкой (`godot`):
   ```go
   // Tap нажимает и отпускает одну клавишу на виртуальной клавиатуре.
   // Возвращает ошибку, если клавиша не поддерживается устройством.
   func (k *Keyboard) Tap(ctx context.Context, code keys.Code) error {
   ```
   Описывайте, *что* делает объявление, смысл неочевидных параметров и результатов,
   какие ошибки возвращаются. Поля структур тоже комментируются.
3. **Каждый логический блок внутри функции** — несколько строк, выполняющих один шаг
   (проверка входных данных, открытие устройства, цикл чтения, отправка, очистка) —
   начинается с комментария, отвечающего на вопрос **«что делает этот блок»**:
   ```go
   // Проверяем, что клавиша входит в возможности этого устройства.
   if !k.caps.Has(code) {
       return fmt.Errorf("tap %s: %w", code, ErrUnsupportedKey)
   }

   // Отправляем нажатие и SYN_REPORT, чтобы композитор увидел событие.
   if err := k.emit(code, keyDown); err != nil {
       return err
   }
   ```
   Тривиальные строки внутри блока отдельно не комментируются — их покрывает комментарий блока.
   Функция из одного-двух выражений (геттер, обёртка) обходится doc-комментарием.
4. **«Почему»** — для неочевидных решений: магические числа, тайминги, ioctl, обходы
   багов композиторов. Со ссылкой на документацию ядра, протокола или issue:
   ```go
   // Ждём 100 мс после создания устройства: композитору нужно время, чтобы
   // подхватить новое устройство, иначе первые события теряются (SPEC FR-VD-2).
   ```

## Чего не делать

- Не пересказывайте код построчно (`i++ // увеличиваем i`).
- Не оставляйте закомментированный код — для истории есть git.
- Не оставляйте устаревшие комментарии: при изменении кода обновляйте комментарий. Устаревший комментарий — это баг.

## Фронтенд

- Каждый Svelte-компонент начинается с HTML-комментария-шапки: что показывает, какие props.
- Функции и экспортируемые константы — JSDoc-комментарий (`/** … */`).
- Логические блоки в скриптах и разметке — комментарии, как в Go (`// …`, `<!-- … -->`).

## Автоматические проверки

| Что | Чем |
|---|---|
| Doc-комментарии у экспортируемых объявлений и пакетов | `revive` (`exported`, `package-comments`) |
| Точка в конце комментариев объявлений | `godot` |
| Форматирование Go | `gofmt`, `goimports` |
| Границы модулей | `internal/archtest` |
| Форматирование и правила фронтенда | `prettier`, `eslint`, `svelte-check` |

Комментарии к логическим блокам и неэкспортируемым объявлениям линтеры не проверяют —
это проверяется на ревью (`AGENTS.md` §1, Definition of Done).
