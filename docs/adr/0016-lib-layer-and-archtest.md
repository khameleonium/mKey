# ADR-0016: Слой чистых библиотек internal/lib и архитектурный тест вместо depguard

- **Статус:** принято
- **Дата:** 2026-09-30
- **Связано:** SPEC.md §4.3, D12; T0.7

## Контекст

SPEC требовал проверять границы модулей линтером `depguard`. При реализации выяснилось:

1. `depguard` не умеет правило «модулю можно импортировать собственные подпакеты
   (`internal/desktop/x11` → `internal/desktop`), но нельзя — чужие модули».
2. Часть кода — не модули с жизненным циклом, а чистые библиотеки (таблица клавиш,
   парсер DSL, часы, сведения о сборке). Если считать их модулями, модулям придётся
   ходить к ним через контракты, что бессмысленно усложняет код.

## Решение

1. Чистые библиотеки без состояния уровня программы живут в `internal/lib/<name>`
   (`internal/lib/keys`, `internal/lib/dsl`, `internal/lib/clock`, `internal/lib/buildinfo`).
   Их может импортировать кто угодно; сами они импортируют только другие библиотеки.
2. Границы проверяет тест `internal/archtest` (часть `go test ./...` и `make lint`):
   - `internal/lib/*` → только `internal/lib/*`;
   - `internal/contracts` → только `internal/lib/*`;
   - инфраструктура ядра (`bus`, `i18n`, `registry`) → только `contracts` и `lib`;
   - модуль `internal/<X>` → `contracts`, `registry`, `bus`, `i18n`, `lib` и свои подпакеты;
   - `internal/app` (сборка программы) → всё.
   Тестовые файлы (`_test.go`) не проверяются: тестам можно собирать модули с фейками.
3. `depguard` не используется.

## Последствия

- Правило точнее и не требует внешних инструментов; нарушение видно как обычный упавший тест.
- Пути пакетов в SPEC обновлены: `internal/keys` → `internal/lib/keys`, `internal/dsl` → `internal/lib/dsl`.

## Альтернативы

- `depguard` с отдельным правилом на каждый модуль — громоздко и легко забыть обновить.
- `go-arch-lint` и аналоги — лишняя зависимость ради простой проверки.
